# animal-drug-safety

A small end-to-end pipeline on public FDA data about adverse events in animals treated with
veterinary drugs. It loads every report since 2016 into SQLite, checks data quality, trains a model
that ranks new reports by how likely they are to be *serious*, and serves the result through a REST API.

> **Disclaimer.** The data comes from [openFDA](https://open.fda.gov/apis/animalandveterinary/event/).
> Reports are unvalidated, and a report does not show that a drug caused an event. This is a learning
> project and must not be used for clinical or regulatory decisions.

## What it does

1. **ETL** (`etl/`): downloads the quarterly openFDA files, cleans the records (units, types,
   ingredient names, list-or-string fields), and upserts them into SQLite. Re-running is safe:
   unchanged files are skipped by SHA-256, and a changed report replaces its old rows.
   Twelve data-quality checks run after every load and fail the run if something is wrong.
2. **Triage model** (`ml/`): predicts whether a report is serious from the details known when it
   arrives: species, age, weight, route, ingredients, reaction terms and so on.
   Logistic regression is the baseline, compared with a small neural network (scikit-learn `MLPClassifier`).
3. **Signal screening** (`stats/`): PRR and ROR with chi-squared for every ingredient × reaction pair,
   using the Evans criteria (a ≥ 3, PRR ≥ 2, χ² ≥ 4). The counts are computed in SQL.
4. **API** (`app/`): FastAPI with `/triage`, `/signals`, `/stats` and `/health`.

## Results

Data: openFDA export of 2026-11-09, 2016 Q1 to 2026 Q2, i.e. **744,473 reports** from 42 files.
Parsing and loading them takes about 75 s on a laptop once the files are downloaded. No records were
rejected, and all quality checks pass (`reports/quality_report.json`).

The data is split by year, so the model is always tested on reports newer than the ones it learned from:
train 2016–2022 (404k), validation 2023 (55k), test 2024–2026 (163k).

| Model | Val PR-AUC | Test PR-AUC | Test ROC-AUC | Test Brier |
|---|---|---|---|---|
| Logistic regression (baseline) | 0.811 | 0.803 | 0.875 | 0.138 |
| MLP, 1 hidden layer of 64 (selected on validation) | 0.912 | **0.895** | **0.932** | 0.100 |

- Serious reports make up 37% of the test set, so a random ranking would score a PR-AUC of about 0.37.
- The MLP result is stable: across three random seeds, test PR-AUC stayed between 0.895 and 0.898.
  For the baseline, changing C from 0.5 to 50 moved validation PR-AUC by less than 0.001.
- The alert threshold was chosen on 2023 data to catch 90% of serious reports.
  - On 2024–2026 it caught 88.9%, while flagging 44% of reports (logistic regression needed 52%).
- Over the whole test period, the death/euthanasia rule plus the model reach PR-AUC 0.924 and recall 0.907.
- Input drift between the training and test years is low (PSI < 0.1). The exception is reporter type,
  with a moderate shift (PSI 0.10).
- The MLP is over-confident at the top: when it predicts 0.86, the observed rate is 0.72.

Full numbers are in [`reports/model_card.md`](reports/model_card.md), generated by the training script.

## Design notes

- **Label leakage.** Seriousness is defined partly by death. Reaction terms such as "Death" or
  "Death by euthanasia", and outcomes "Died" or "Euthanized", would give the answer away.
  - Reports containing them (7% of the test set) skip the model; a simple rule sends them to review.
  - That rule is right 98.8% of the time.
  - The model is trained and scored only on the remaining reports, so its metrics are not inflated.
- **No train/serve skew.** Training data (from SQLite) and API requests go through the same
  `report_features()` function. A test checks that one report produces identical features both ways.
- **Versioning.** The model version is the training date plus a hash of the loaded files.
  - The model file, its metadata and the model card are written together.
  - The API reports which version answered.
- **Monitoring.** PSI is computed on the main inputs and on the model score, comparing training data with newer data.

## Signal screening caveat

Of the 174,707 ingredient × reaction pairs with at least 3 reports, about 62% pass the Evans criteria.
The screen is very sensitive on this data, for two reasons:
- Reaction terms are tied to drug classes (for example, lack of efficacy for antiparasitics).
- Only pairs that already co-occur are tested.

A flag is a question for a reviewer, not a finding. Better next steps would be stratifying by species
(`--species`) and adding Bayesian shrinkage (EBGM or the information component).

## Run it

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
make data       # ~140 MB download, builds data/ads.db (~0.9 GB) and the quality report
make train      # ~1 min; writes models/ and reports/
make signals
make serve      # http://localhost:8000/docs
make test
```

Example request:

```bash
curl -s -X POST localhost:8000/triage -H 'content-type: application/json' -d '{
  "species": "Dog", "age_years": 11, "reporter": "Veterinarian", "type_info": "Safety Issue",
  "routes": ["Oral"], "ingredients": ["Meloxicam"], "reactions": ["Vomiting", "Melaena"]}'
```

Docker (mount the data and model built above):

```bash
docker build -t animal-drug-safety .
docker run -p 8000:8000 -v "$PWD/data:/app/data" -v "$PWD/models:/app/models" animal-drug-safety
```

CI (GitHub Actions) runs lint and the tests, then a smoke run of the real pipeline on one quarter
(including a second run that must skip the unchanged file), then a Docker build with a health check.
The tests use synthetic records only.

## Layout

```
etl/      download.py  parse.py  db.py  quality.py  run.py
ml/       features.py  train.py  drift.py
stats/    signals.py
app/      main.py
tests/    60 tests (parsing, idempotent loads, quality gates, leakage, PRR/ROR maths, training, API)
reports/  model_card.md  metrics.json  quality_report.json
```
